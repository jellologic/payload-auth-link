# Security model — the credential-path matrix

Every way a session or credential for the users collection can be
created or used, and the controls that govern it. The REST walk of
the account-control rows (1–7, 9, 10, 16) lives in
`packages/plugin/src/__tests__/integration-credential-paths.test.ts`
and its GraphQL twin (row 11: rows 1, 3–7, 9, 10, 16 over Payload's
real GraphQL schema) in `integration-credential-paths-graphql.test.ts`.
The remaining rows are pinned where their surface lives: rows 8, 13
and 14 (linkable proof, `setEmail` resync) in
`integration-access.test.ts` and `repository.test.ts`, 12 in the
REST walk (the Local API cases), 15 in
`integration-impersonation.test.ts`, 17 in `endpoints.test.ts` and
`e2e/csrf.spec.ts`, 18–20 in `integration-server-sessions.test.ts`,
`server-failures.test.ts`, and the real-engine
`server-sessions-engine.test.ts` / `server-gates-engine.test.ts` /
`server-mint-gates-engine.test.ts`
(Better Auth) and `oauth.test.ts` (Auth.js), 21 in
`integration-legacy-coexistence.test.ts`. A new credential path
cannot ship without a row here and a test that walks it.
Rows 30–34 (surfaces outside any collection operation, for every
Payload-issued credential of a dead account: a suspended user's API
key, a key re-enabled on a linked document, a pre-link JWT without
`useSessions`, a suspended JWT) are walked in
`integration-local-credential-gate.test.ts`; a renamed
`suspendedUntilField` in `integration-suspension-field-rename.test.ts`.
Rows 22–23 are walked on a real engine with `auth.verify` in
`integration-verified-linking.test.ts` (plus
`integration-prelink-jwt-stateless.test.ts` for hosts without
`useSessions`); row 10a in `integration-prelink-api-key.test.ts`
(and `integration-prelink-api-key-opt-in.test.ts` for
`allowLocalCredentialsForLinkedDocs`); rows 24–25 in
`integration-organizations-governance.test.ts`; row 26 in
`packages/web/src/__tests__/verify.test.ts`; row 28 in
`packages/provider-authjs/src/__tests__/session-shape-engine.test.ts`
(Auth.js) and
`packages/provider-better-auth/src/__tests__/session-json-engine.test.ts`
(Better Auth);
row 29 (Better Auth only) in
`packages/provider-better-auth/src/__tests__/mfa-step-up-engine.test.ts`.

## Real-engine pins (issue #84)

The walks above use the plugin's stub provider. Each row is ALSO
pinned against a real engine — real Better Auth 1.7 / real
`@auth/core` 0.41 on Payload SQLite in memory behind a real
`authLink` boot — with its success path and its failure paths
(wrong password or token, expired or revoked session, another
user's credential, suspended user, unproven email, pre-link JWT,
missing CSRF proof). The walk files are, on Better Auth,
`packages/provider-better-auth/src/__tests__/credential-paths-engine.test.ts`
(**BA walk**: rows 8, 12–14, 19) and
`credential-paths-rest-engine.test.ts` (**BA REST walk**: rows 2
default policy, 3–7, 10, 10a, 16, 22–27; BA's `bearer()` plugin installed,
cookie-only policy), plus the channel walks
`channel-bearer-engine.test.ts` (**BA bearer walk**:
`admitChannels: ['cookie', 'bearer']`) and
`channel-api-key-engine.test.ts` (**BA api-key walk**:
`@better-auth/api-key` with `enableSessionForAPIKeys`,
`admitChannels: ['cookie', 'api-key']`); on Auth.js,
`packages/provider-authjs/src/__tests__/credential-paths-engine.test.ts`
(**Auth.js walk**: database sessions, a magic-link provider).
Other files live in the same `__tests__` directory as their engine.

## Known residuals (documented, not exploitable)

- **The MFA projection for local sessions lives at the operation and
  access layer.** A live local JWT or API key holding a
  `requireMfaForRoles` role keeps that role on `req.user` inside a host
  custom endpoint (no operation runs there to withhold it); every
  Payload operation and the users permission map withhold it. Host
  endpoints that authorize on such a role should check
  `sessionMfaSatisfied` / `denyWithoutMfa`. Suspension and the
  provider-owned default are NOT residuals: a dead account's local
  credential resolves no user at all (rows 30–34).
- **A forged local JWT naming a dead account** arms the credential
  gate for that document id, and Payload then refuses the forgery
  before reading the document — so the gate stays armed for the rest
  of that (anonymous) request, and a host Local-API read of that one
  document with the same `req` and `overrideAccess` fails. Only the
  forger's own request is affected.
- **Host-collection permission MAPS can overstate for a local
  session holding an MFA-policy role** — their access functions are
  the host's, so the projection cannot reach the map; the actual
  operations are gated (row 4). The users collection's map is
  truthful (row 16).
- **Fabricated requests in tests** (access functions invoked with a
  bare `{ user }` req) skip the belt — not a request pipeline; real
  requests always carry `payload`.

## Threat-model notes

- The last three advisories were each an ADJACENT credential path
  (field access → email change → forgot/reset). When adding any
  credential-adjacent feature, walk this matrix first.
- Suspension is the account-control lever of last resort: it is
  enforced on every strategy, at authentication time, with a fresh
  read — a pre-existing local JWT or API key resolves no user from the
  next request on, on every surface (GHSA-mjvh: enforcing it per
  collection left file routes, custom endpoints, `payload.auth()`,
  preferences and `/access` open).
- A refused email link (an unproven document holds the address) is
  an OPERATOR decision. A fresh verification of the address proves
  who controls the address, not who built the document: on a squatted
  document the mail reaches the victim, and granting the proof on
  that click would hand the victim's sign-in the squatter's document.
  Confirm who created and owns the document; rename or remove it when
  it is not the address owner's.
- Provider-linked documents are provider-owned by default: exactly
  one credential owner per document. The escape hatch
  (`allowLocalCredentialsForLinkedDocs`) exists for migration windows
  only.
- **Enrolling the first second factor needs only the password**
  (Better Auth's `/two-factor/enable`). The session that enrols gets
  no MFA proof from it (row 29), but whoever holds only the password
  of a user who never enrolled can still enrol their own authenticator
  and then sign in with it. `requireMfaForRoles` is only as strong as
  the enrolment: grant an MFA-gated role to a user who has ALREADY
  enrolled (check `twoFactorEnabled` on the provider user first), or
  enrol them through a channel you trust (in person, a verified
  recovery flow), never to a password-only account.
- **Migration manifests drive `overrideAccess` writes** (the
  `@payload-auth-link/migrate` rollback restores roles, identities and
  the linking proof). A manifest is signed, bound to its database and
  run, and every captured value is sealed FOR that run (the database
  id and run nonce are AES-GCM associated data), so a value copied
  into another manifest opens nowhere. An unsigned (pre-0.6.0)
  manifest is refused on any database that has run migrate 0.8.0 or
  later, for rollback and finalize alike (GHSA-xw9m-ph95-84rx).
  Residual: a database CLONED after its first `--apply` carries the
  original's migration record. On Postgres a clone in another cluster
  or under another database name is detected from the server itself
  (`system_identifier` + `current_database()`); a physical copy of the
  whole cluster (disk snapshot, promoted replica), and any clone on
  SQLite or MongoDB, is detected only when each environment states
  its own `--environment-id` from before its first `--apply`. Values
  sealed by migrate 0.8.0 and earlier are bound to their entry only;
  they open only inside a manifest the kit signed, or an unsigned one
  on a database that never ran 0.8.

## Single-host deployments: `__Host-` session cookies

Better Auth's default cookie names carry at most the `__Secure-`
prefix, never `__Host-`. A `__Secure-` cookie may still be set by a
sibling subdomain with `Domain=.example.com` ("cookie tossing"), so a
compromised or user-content subdomain can plant its own session
cookie in the browser — a login-fixation vector. When the app is
served from exactly one host (no `crossSubDomainCookies`), opt in to
`__Host-` names, which browsers only accept with `Secure`, `Path=/`,
and no `Domain` — a sibling cannot set them:

```ts
// The SAME options go to the engine and to every cookie-name helper
// (middleware, `getBetterAuthSessionCookieNames`), so names agree.
const cookieOptions = {
  advanced: {
    // The prefix becomes part of every name: `__Host-ba.session_token`.
    cookiePrefix: '__Host-ba',
    // Turns off ONLY Better Auth's automatic `__Secure-` name prefix
    // (it would produce `__Secure-__Host-…`); the attributes below
    // keep every cookie Secure.
    useSecureCookies: false,
    defaultCookieAttributes: { secure: true, path: '/' },
    // Never set `domain` or `crossSubDomainCookies` with `__Host-`.
  },
}
createBetterAuthEngine({ options: { ...cookieOptions /* , … */ } /* , … */ })
getBetterAuthSessionCookieNames(cookieOptions) // ['__Host-ba.session_token']
```

Logout clears these names with `Secure; Path=/` and no `Domain`, as
browsers require. Changing the prefix renames the cookies: existing
sessions read as signed out once, so roll it out like any
session-cookie change. Browsers accept `Secure` cookies on
`http://localhost`, so local development keeps working.
